# 跨场景判断示例

以下为方法示例，不预设任何真实项目的能力或本期范围。

## 已有网页新增列表筛选

需求是在现有列表按状态筛选。接口已支持状态参数，界面尚未传参。

核对筛选是否作用于全部分页数据、返回语义是否符合要求。若支持，只补前端交互、参数和验收，不新增查询接口。若前端只能筛当前页而需求要求全量筛选，不能为减少任务把局部过滤当成已满足。

## 文件上传后用于业务处理

已有上传和内容提取，业务请求没有 file 字段。

核对既有文件 ID、记录关联或内容传递路径。字段不存在不直接推出需新建上传解析系统；已有上传也不证明业务处理能取得内容。只补实际断开的关联或传递，并按要求验证格式、权限和错误行为。

## 新建预约应用

项目无现有代码，需求只明确选择时段、提交预约和查看结果。

先明确可用的身份、时段数据来源、预约冲突规则和交付端。围绕用户流程拆必要交付；不默认增加营销系统、推荐引擎、多租户平台。若多个用户不能预约同一时段，冲突处理是核心正确性要求，不能当成可省略的增强项。

## 同名能力语义不同

现有“取消”会立即终止运行，需求却要求当前操作完成后停止后续操作。

核对执行边界和结果保存，而非仅看接口名称。语义不同构成真实改造任务，优先复用既有控制机制，不重建整套调度系统。停止后的额外内容生成只有被需求要求时才纳入。

## 状态显示与可观察性

产品希望区分两个处理阶段，但底层只有开始、结束事件，中间耗时无法可靠归因。

先核查是否存在可靠信号；若没有，将阶段识别列为可行性核查或明确展示方案选择，不直接安排状态字段、推送、持久化全套实现。

## 后续决策改变范围

早期草稿由客户端保存，后来明确要求跨设备恢复。

重新检查服务端是否已有草稿存储和同步能力。若缺失，新增必要服务端任务；不能继续沿用“客户端负责”排除它，也不能自动扩大成多人实时协同。用户删除某个功能后，同步删除它派生的协议、存储、测试和排期，保留仍被其他功能需要的公共部分。
